# Изолированный модельный шлюз Hermes — этап настройки

Состояние: модельный шлюз и CLI-запуск через Unix socket. Paperclip и адаптеры трёх
приложений ещё не подключены. Установка не означает готовность всего агента.

Hermes использует network_mode: none и не получает ключ OpenAI. В его контейнере
работает loopback HTTP -> Unix bridge. Шлюз OpenAI — отдельный непривилегированный
контейнер с исходящей сетью; публичных портов у него нет. Только он читает ключ.
Ключ в запрос агента/аргументы CLI не попадает. Общий каталог сокета монтируется
Hermes read-only, чтобы он не мог заменить сокет или создать в нём файлы.

Шлюз разрешает только текстовый Chat Completions для gpt-4o-mini и локальный список
разрешённых моделей. Запрещены Files, Responses, отправка почты, произвольные URL,
редиректы, изображения по ссылкам и серверные инструменты. Function tools здесь
лишь описание функций для модели, не право выполнять внешние действия.

Проверки: 11 unittest, lint и Docker Compose config прошли локально. Реальный запрос
с ключом пользователя и запуск на его VPS проверяются после установки.

Предохранители: 2 одновременных запроса, 20 запросов/мин, ограниченные размер запроса
и длина ответа. Это защита нагрузки, а не механизм запрета публикаций.
Жёсткие суточные квоты выключены по умолчанию. При необходимости оператор задаёт
DAILY_REQUEST_LIMIT и DAILY_INPUT_BYTE_LIMIT только шлюзу. Их счётчики сохраняются
в SQLite и не сбрасываются при перезапуске. Это не точный финансовый лимит в долларах.

Установка на уже подготовленный VPS:

1. Получить эту ветку в отдельный /srv/hermes-stack/deployment-source.
2. `sudo python3 agent-stack/prepare.py` (из deployment-source).
   Ключ копируется из работающей CRM, если найден; иначе запрашивается скрытым вводом.
   Исходный .env CRM не изменяется. Нет копирования остальных ключей и BotFather token.
3. `docker compose -f agent-stack/compose.yaml config --quiet`.
4. `docker compose -f agent-stack/compose.yaml up -d model-proxy`.
5. `docker compose -f agent-stack/compose.yaml exec -T model-proxy /opt/hermes/.venv/bin/python /opt/workspace-agent/probe_gateway.py`.
   Проверка не выполняет вызовов OpenAI.
6. Первый модельный тест: `docker compose -f agent-stack/compose.yaml run --rm -T hermes chat -q 'Ответь ровно: МОДЕЛЬ ПОДКЛЮЧЕНА'`.
   Это уже разрешённая передача синтетического запроса в OpenAI, без рабочих данных.

В окружении Google SSH используйте `sudo docker --host=unix:///var/run/docker.sock`.
Не запускайте Paperclip с trusted-local UI на публичном адресе. Его запуск и связка
с Hermes — следующий отдельный этап. Существующий бот CRM сохраняет свой webhook.
Не предоставляйте агенту docker.sock или каталоги существующих сервисов.

## Первый запуск Paperclip без публикации панели

`prepare_paperclip.py` создаёт только собственные секреты Paperclip и его БД,
повторный запуск не меняет пароли. `compose.paperclip.yaml` добавляет отдельную
PostgreSQL и Paperclip с аутентификацией, отключённой регистрацией/телеметрией,
выключенным scheduler агентов и отдельной внутренней сетью. Ключ OpenAI и папки
рабочих сервисов Paperclip не получает. На хосте открыт только 127.0.0.1:3101.

```bash
sudo python3 prepare_paperclip.py
sudo docker --host=unix:///var/run/docker.sock compose \
  -f compose.yaml -f compose.paperclip.yaml \
  up -d --wait --wait-timeout 240 paperclip-db paperclip
```

Это подготовительный закрытый запуск; учётная запись владельца и внешний защищённый
доступ настраиваются следующим шагом. Browser localhost на компьютере пользователя
не относится к localhost VPS. Не открывайте порт 3101 в Google Cloud firewall.
Пароли/claim-ссылки и полные разрешённые Compose env-конфигурации не присылаются в чат.

## Создание владельца

`sudo python3 bootstrap_owner.py` запрашивает email/имя и дважды пароль (скрыто).
Использует штатный `bootstrapCeoInvite` выбранной версии Paperclip, а не прямую
запись роли/хеша пароля в БД. Одноразовая ссылка остаётся внутри процесса и не печатается.
На время запроса учётной записи регистрация включается только у локального контроллера;
Paperclip остаётся на 127.0.0.1:3101. В finally восстанавливается закрытая регистрация;
при ошибке восстановления контроллер останавливается. Не закрывайте SSH до завершения.
Ни один из старых сервисов не перезапускается.

Подключение использует фиксированный localhost, игнорирует HTTP_PROXY и запрещает
редиректы; пароль не попадает в аргументы docker/node, env или лог команды.
Повторное назначение при уже существующем администраторе не выполняется.
Внешняя публикация по HTTPS на этом шаге отсутствует.

## HTTPS для личной панели

После успешного создания владельца: `sudo python3 publish_paperclip.py`.
Адрес по умолчанию — `https://agents.34.22.184.67.sslip.io`.
Скрипт проверяет DNS, сохраняет приватную резервную копию Caddyfile и своего `.env`,
валидирует добавленный блок внутри действующего Caddy и перезагружает его без остановки.
Существующие маршруты сохраняются. Пароли владельца не запрашиваются.
При ошибке восстанавливаются прежние маршруты и настройки панели.
Сертификат выпускается Caddy через Let's Encrypt; конечный HTTPS и вход нужно проверить
в браузере после установки. Наличие сертификата локальными тестами не подтверждается.

Origin панели сохраняется в игнорируемом Git файле `agent-stack/.env`, поэтому обычные
команды Compose с двумя исходными файлами сохраняют адрес и закрытую регистрацию.
Контроллер и Caddy получают отдельную внутреннюю сеть `paperclip-web`;
БД остаётся только в `paperclip-control`, Hermes по-прежнему имеет `network_mode: none`.
Подключение действующего Caddy к сети сохраняется при restart, но при **пересоздании**
его контейнера нужно снова выполнить `publish_paperclip.py` для восстановления подключения.
Этот шаг публикует панель управления, но ещё не подключает Hermes к задачам Paperclip
и данным трёх приложений. Scheduler агентов остаётся выключенным.
После публикации `bootstrap_owner.py` больше не требуется и с прежним localhost Origin
не используется; учётная запись уже создана.

## Первый внутренний Hermes Gateway (только текст)

После готовности Paperclip выполните `sudo python3 prepare_hermes_gateway.py`.
Три файла Compose применяются вместе: `compose.yaml`, `compose.paperclip.yaml`,
`compose.hermes-gateway.yaml`. Запускаются `hermes-runtime` и `hermes-paperclip-bridge`.
Сборка образов повторно не нужна. Runtime использует штатный `APIServerAdapter`
закреплённой версии Hermes, собственное хранилище и конфигурацию; Telegram/scheduler
Hermes на этом шаге не запускаются. Инструменты выключены, неожиданное их включение
прерывает запуск/создание агента. Данные трёх приложений ещё не подключены.

Paperclip обращается к `http://127.0.0.1:8642` в своей сетевой namespace.
Sidecar, разделяющий эту namespace, передаёт только health/models/capabilities,
создание текстового run, чтение результата/событий и остановку через Unix socket.
Hermes остаётся с `network_mode: none`, не видит Docker, секрет OpenAI или папки
приложений. Через мост запрещены Files, cron/jobs, сессии/профили, одобрение tool calls,
произвольные URL, смена провайдера и параметров сети в запросах.
Отдельный API_SERVER_KEY лежит в `/srv/hermes-stack/private/hermes-gateway.key`;
он не является OpenAI key и не выводится подготовкой/проверками.

```bash
sudo docker --host=unix:///var/run/docker.sock compose \
  -f compose.yaml -f compose.paperclip.yaml -f compose.hermes-gateway.yaml \
  up -d --wait --wait-timeout 180 hermes-runtime hermes-paperclip-bridge
sudo docker --host=unix:///var/run/docker.sock compose \
  -f compose.yaml -f compose.paperclip.yaml -f compose.hermes-gateway.yaml \
  exec -T hermes-runtime /opt/hermes/.venv/bin/python /opt/workspace-agent/probe_hermes_gateway.py
```

Проверки не выполняют задач и не вызывают OpenAI. Успешный health не подтверждает
работу модели: отдельный синтетический run и результат проверяются следующим этапом.
Реальный запуск native runtime проверяется на VPS; локальные тесты покрывают транспорт,
авторизацию, подготовку секрета и Compose. В Paperclip прежний API key OpenAI не вводится.
При пересоздании Paperclip также пересоздавайте `hermes-paperclip-bridge` (общая namespace).
Пока адрес и отдельный секрет не настроены в карточке агента, Finish setup не выполняется.

## Русские ответы и передача текущей задачи на проверку

`sudo python3 install_task_control.py` выполняется после успешного текстового теста
и завершения активных задач Hermes. Сборка образов не нужна. Используются четыре
Compose-файла: исходные три и `compose.task-control.yaml`. При последующих up/recreate
Hermes API используйте все четыре файла, чтобы сохранять инструменты текущей задачи.
Установка не меняет API_SERVER_KEY (его ручная ротация сейчас отложена пользователем).

В доверенные инструкции каждого запуска Paperclip добавляется русский язык и указание
передать результат через `mcp_paperclip_task__submit_result`. Включены только два локальных
MCP-инструмента: проверить текущую задачу и передать результат в `in_review`.
`trust: full` действует только для этих двух методов контроллера, которые выполняются
внутри сервера. Остальные toolsets, терминал, произвольные URL и отправка данных выключены.
Запрет сетевого доступа runtime остаётся `network_mode: none`.

Доверенный контроллер исполняется отдельно от агента, с доступом к собственной БД
Paperclip и ключом штатного agent API. Этот ключ имеет native scope `standard`,
**не** `task_bridge`: последний требует заранее назначенного project/parent boundary,
которого пока нет в пользовательском потоке задач. Полномочия дополнительно ограничены
неизменяемым контроллером: агент не получает ни этот ключ, ни DB credential.
Контроллер не имеет API для произвольных запросов или выполнения кода.

Мост Paperclip выдаёт HMAC-разрешение на 30 минут, привязанное к Idempotency-Key
конкретного запуска. Сам ключ подписи агенту не доступен. Контроллер проверяет подпись,
активный запуск в БД, компанию/агента, issue binding, назначение исполнителя и текущий
executionRunId. Клиент не может передать другой task id, новый статус или URL.
Единственная мутация — штатный PATCH текущей задачи с `status: in_review` и кратким
комментарием через Paperclip API с `X-Paperclip-Run-Id`. Native проверки API сохраняются.
Терминальный Done, одобрение, отправка писем и публикация недоступны.

Проверка `probe_task_control.py` выполняет health и только заведомо запрещённые запросы:
не вызывает OpenAI и не меняет задачи. Новый реальный тест должен разрешать локальные
инструменты задачи (не включайте прежнее «не используй инструменты»). Ожидается русский
ответ и переход в «На проверке». Это проверяется на VPS после установки: локальные
тесты не доказывают совместимость всех native runtime компонентов в работающем образе.
При ошибке установки скрипт восстанавливает предыдущую конфигурацию/состав контейнеров;
настройки трёх приложений, исходный ключ OpenAI и Telegram CRM не затрагиваются.
