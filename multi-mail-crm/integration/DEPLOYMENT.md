# Третья вкладка в существующем Play Scout + помощнике

Сохранены исходные инструменты:

- Play Scout: `play-scout-workspace`, `3e429fe73c99d044fcbfa7ddfa6260ba9c354e1e`.
- Помощник регистраций: `registration-assistant`, `f4319a0c27e8d3a8c3ec38a7167aa172a353cdf1`.

**Их исходники и данные не редактируются.** Шлюз добавляет один пункт навигации
в HTTP-ответы `/theme.js` и `/assistant/`. Для остальных страниц и API тело
передаётся без изменений. Сохраняются прежние Basic/Workspace/Bearer-проверки старых
инструментов. Только новая почтовая CRM открывается без входа.

## Новая локальная установка для проверки

```sh
python3 scripts/init_env.py
python3 scripts/verify_tool_sources.py
docker compose --profile integrated up --build -d --wait
```

Откройте `http://localhost:3000/crm`: появятся три вкладки. Новая CRM —
`http://localhost:3000/mail-crm/`. Play Scout и помощник здесь — отдельные локальные
копии указанных коммитов с НОВЫМИ томами. Такой профиль не переносит и не заменяет
данные вашего существующего сервера. Сборка помощника загружает его зависимости OCR.

## Добавление на уже работающий VPS

На имеющемся VPS **не запускайте профиль `integrated`**: иначе создадите лишние
копии двух старых приложений. Сначала разместите этот каталог, например, в
`/srv/mail-crm`. Нужен Docker Compose >=2.24.4. Дальнейшие команды выполняет
администратор по SSH, не браузер и не ссылка на другой диалог.

1. Сохраните обычную резервную копию старого рабочего пространства его прежним
   механизмом. Проверьте, что текущие два инструмента работают.
2. В `/srv/mail-crm` выполните подготовку. Скрипт ЧИТАЕТ старые env-файлы, импортирует
   только совместимые переменные в НОВЫЙ `.env`, сохраняет уже заданные ключи CRM.
   Значения секретов не выводятся. Файлы Play Scout/помощника не перезаписываются.

   ```sh
   python3 integration/prepare_existing.py --public-url https://play-scout.34.22.184.67.sslip.io
   python3 scripts/verify_tool_sources.py
   docker compose -f docker-compose.yml -f integration/compose.existing.yml up --build -d --wait
   ```

   По умолчанию используются `/srv/play-scout/app.env`,
   `/srv/play-scout-workspace/workspace.env` и сеть `play-scout_default` — именно
   пути из предоставленной ветки помощника. Другие пути задаются параметрами
   `--scout`, `--workspace`; другое имя сети — `PLAY_SCOUT_DOCKER_NETWORK` в `.env`.
   Ключи, которых нет в старом env, нужно заполнить в новом `.env`; они не выдумываются.

3. В существующей конфигурации Compose рабочего пространства добавьте **отдельный
   override только для Caddy** (например, `/srv/play-scout-workspace/mail-crm.proxy.yml`):

   ```yaml
   services:
     caddy:
       volumes:
         - /srv/mail-crm/integration/Caddyfile:/etc/caddy/Caddyfile:ro
   ```

   Новый Caddyfile сохраняет TLS, лимит загрузок 350 MB, forward_auth, расширение
   Dolphin и прежний Workspace-key. Меняются только upstream через новый шлюз
   и добавляется `/mail-crm/`. Не заменяйте домен и секреты существующего проекта.

4. Проверьте итоговую конфигурацию старого проекта с его ПРЕЖНИМИ base-файлами,
   env-файлами и новым override. Список прежних base-файлов находится в
   `/srv/play-scout-workspace/base-files.list`, команда их сборки — в прежнем
   `workspace.sh`. Сначала `config --quiet`, затем проверка Caddyfile. После
   проверки примените изменение **только к Caddy**:

   ```text
   docker compose <прежние --env-file и -f> -f /srv/play-scout-workspace/mail-crm.proxy.yml --profile public up -d --no-build --no-deps caddy
   ```

   Это шаблон команды: угловые скобки заменяются фактическими аргументами вашего
   существующего развёртывания. Нельзя запускать `up` для старых `app` и
   `registration-assistant` или пересобирать их ради добавления CRM. Caddy может
   кратковременно переподключить клиентские соединения; приложения и их тома не меняются.

5. Проверьте старые `/crm`, `/assistant/`, загрузки/расширение и новую `/mail-crm/`.
   Сравните IDs и image IDs контейнеров `app` и `registration-assistant` до и после:
   они должны совпасть. Добавьте новый override к вашему дальнейшему обслуживанию
   шлюза, чтобы следующий restart/update Caddy не вернул старую конфигурацию.

## Откат добавления

Верните Caddy его прежний bind mount/config через прежние compose-файлы и примените
только сервис Caddy. Остановите НОВЫЙ проект CRM без `-v`. Ни старые контейнеры,
ни JSON-база Scout, ни SQLite/документы помощника не удаляются. Данные новой CRM
также сохраняются в её отдельных томах.

## Что здесь не выполнено

Публикация на живом VPS не выполнялась: эта среда не получила SSH-доступ из другого
диалога Codex. Публичная ссылка и ветки дают исходники, но не доступ к секретам и
файлам сервера. Ссылки ChatGPT и живого помощника блокируются сетевым прокси этой среды.

## Автоматическая команда для администратора VPS

При стандартной структуре `/srv/play-scout` и `/srv/play-scout-workspace` предыдущие
шаги выполняет проверяемый скрипт:

```sh
sudo bash /srv/mail-crm/integration/install-existing.sh https://play-scout.34.22.184.67.sslip.io
```

Он проверяет версии установленных runtime-файлов, сохраняет конфигурацию отката,
запускает только НОВЫЕ сервисы, проверяет Caddyfile и применяет только Caddy. IDs
и image IDs старых приложений должны остаться прежними. Если проверка новой CRM
провалится, скрипт возвращает прежнюю конфигурацию прокси. Новые тома не удаляются.
При следующих обслуживаниях Caddy учитывайте записанный `active-override`; старый
`workspace.sh` автоматически не редактируется.
