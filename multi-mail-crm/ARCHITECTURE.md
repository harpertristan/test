# Архитектура и решения

## Сервисы

Новая CRM имеет шесть базовых сервисов: `postgres`, `redis`, `api`, `worker`,
`beat`, `frontend`. API применяет миграции до старта двух Uvicorn-процессов; остальные
прикладные сервисы ждут его readiness. PostgreSQL и Redis не публикуют порты хоста.
Frontend отдаётся непривилегированным Nginx, `/api` и `/ws` работают на одном origin.

В одном сервисе `worker` запускаются три Celery-группы: `sync` (2 процесса), `classify`
(2 процесса), `control` (1 процесс). Родитель передаёт SIGTERM всем группам и завершает
их при остановке; падение группы приводит к перезапуску сервиса. Медленный LLM не
занимает очередь управления. `beat` должен существовать в одном экземпляре.

Суммарные Compose-лимиты памяти около 6.25 GiB. Общий лимит IMAP дополнительно
ограничен Redis-семафором, по умолчанию 8. Реальная нагрузка зависит от задержек,
объёма писем и квот провайдеров; цифра 300+ проверена для UI, не для VPS-пропускной способности.

## Путь входящего письма

1. Polling каждые 120 секунд либо проверенный webhook создаёт запрос синхронизации.
2. Redis lease исключает одновременную синхронизацию одного аккаунта. Задачи
   распределяются по времени; ключ очереди подавляет повторные постановки.
3. Провайдер читает письмо без изменения флагов: Zoho EU `markAsRead=false`, Gmail
   `messages.get`, IMAP `EXAMINE` + `BODY.PEEK[]`. IMAP сначала проверяет размер.
4. Письмо и запрос дальнейшей обработки сохраняются одной транзакцией. Курсор
   обновляется только после сохранения пакета. Уникальность `(account_id, remote_id)`
   предотвращает повторный импорт. IMAP учитывает UIDVALIDITY; Gmail — historyId,
   pageToken и ограниченный повторный импорт при устаревшем historyId.
5. Classifier получает только текст и тему. Письмо считается недоверенными данными.
   OpenAI получает `response_format={"type":"json_object"}`; результат проверяет
   строгая Pydantic-схема. Есть один исходный вызов и три повтора с backoff 1/2/4 сек.
   Ошибка или невалидный JSON дают `other`, confidence 0, с явной причиной.
6. В транзакции записываются категория, флаг needs_reply, счётчики ящика,
   персональные notifications и события outbox. Блокировка строки аккаунта
   согласует параллельные изменения счётчиков.
7. Outbox-диспетчер доставляет задания в Celery, события в Redis Pub/Sub и IDs
   Telegram-уведомлений в буфер. Недоставленные события остаются в PostgreSQL.
   Отдельная recovery-задача подбирает pending-письма и отложенные отправки.

События WebSocket могут повторяться: клиент дедуплицирует уведомления по ID.
После переподключения клиент перечитывает состояние БД; есть резервный refresh раз
в минуту. Несколько процессов API получают одни события через Redis. Старые
доставленные записи outbox удаляются пакетами; письма и история не удаляются этим заданием.

## Ограничители

Redis token bucket использует время Redis и общий ключ Zoho organization_id,
а не ID одного ящика. Ёмкость bucket равна одному запросу: нет неконтролируемого
стартового burst. Максимум — 30 запросов/мин на организацию, включая чтение контента.
Есть отдельный общий bucket LLM. Распределённые lease имеют срок и продление;
при недоступном Redis новые операции синхронизации не выполняются без ограничений.

Квота 30/мин не совместима с polling 300 ящиков одной организации раз в 2 минуты.
Очередь сохраняет корректность, но не отменяет физическую квоту. Webhook сокращает
пустые опросы; при большом входящем потоке всё равно нужна достаточная квота на контент.

## Непрочитанность и ответы

GET карточки письма не имеет побочного эффекта. Явная команда read/unread сначала
сохраняет желаемый флаг и номер ревизии. Повтор старой задачи не может отменить
более новое решение оператора. Изменение CRM-флага подтверждается после успешной
операции провайдера; незавершённые намерения подбираются recovery-задачей.

`needs_reply` означает неотвеченное входящее `add_request/other`, а возраст считается
отдельно. Порог красной точки — строго больше 48 часов; ровно 48 часов не включает
точку. Дневные индикаторы имеют 3px-полосу; анимации отключаются при reduced-motion.
Реклама, отказ, одобрение и исходящие в overdue не входят. Почасовое задание
пересчитывает условие; интерфейс обновляет возраст независимо от перезапуска сервера.

Отправка использует отдельную строку исходящего и UUID идемпотентности. Статус
`replied_at` меняется после подтверждения провайдера, только для сообщений треда,
существующих до начала отправки. Более позднее входящее не закрывается. После
неопределённого сетевого результата повтор SMTP/API не запускается автоматически.

## Безопасность

- В новой CRM нет входа, JWT-сессий и ролевых ограничений. Все действия выполняются
  от одного технического профиля; его password_hash содержит нерабочий маркер.
  Эндпоинтов login/register/logout/invite/users нет. Ранее сохранённые users не удаляются.
- HTTP сохраняет проверку Origin для браузерных записей, WebSocket — проверку Origin
  и корректного UUID общего профиля. Это не заменяет авторизацию: CRM намеренно
  доступна всем, кто может обратиться к её адресу.
- Старые Play Scout и помощник используют неизменённые исходные механизмы доступа.
  Шлюз сохраняет Authorization/Cookie/Host, forward_auth и Bearer расширения;
  при передаче в новую CRM старые credentials удаляются из заголовков.
- IMAP-пароли и OAuth access/refresh-токены зашифрованы Fernet. OAuth хранится
  JSONB-конвертом `encrypted`; API не отдаёт секретные поля. Ротация ключа требует
  отдельной процедуры перешифрования; простая замена ключа недопустима.
- Inbox.eu host/port закреплены: произвольный IMAP/SMTP SSRF через CRUD не допускается.
- OAuth state одноразовый; проверяется соответствие авторизованной почты ящику.
  Zoho использует только `.eu` endpoints. Refresh выполняется по расписанию и перед запросом.
- Gmail push проверяет RS256 Google OIDC, issuer, audience, email и email_verified.
  Zoho webhook требует отдельного HMAC-derived header. Telegram webhook проверяет
  secret-token, а callback — принадлежность notification Telegram-пользователю.
- Привязка Telegram одноразовая и истекает через 10 минут. Шторм буферизуется
  до окончания окна, поэтому первые пять сообщений не успевают уйти отдельно.
- HTML не выполняется; текст экранируется React. Есть CSP, запрет iframe-встраивания,
  ограничение тела HTTP и отсутствие публичного DB/Redis/metrics-порта.
- В журнал не пишутся тела писем, пароли, OAuth-коды и query string. SQL-параметры скрыты.
  TLS, подписи и проверки хешей при установке не отключаются.

## Этап 2

Таблица `ai_rules`, поля `messages.ai_handled`, `messages.ai_draft` и абстракция
`AIResponder` существуют. `DisabledAIResponder` явно отказывает в выполнении.
Ни одна очередь не запускает AI-автоответы и не выполняет правила автоматически.


## Сосуществование с двумя исходными инструментами

`integration/tools/` содержит полные неизменённые снимки двух указанных коммитов.
Контрольные суммы проверяются отдельно от тестов. Шлюз `integration/gateway` только
добавляет третью ссылку в исходные навигационные ответы; не меняет их API, Cookie,
Host, Bearer расширения и проверки ролей. Для новой CRM credentials старых инструментов
не передаются. Переходы выполняются обычными ссылками, не iframe; CSP/frame-ancestors
старых инструментов сохраняются. Новая БД и очереди изолированы от JSON/SQLite старых.

Профиль `integrated` — локальные копии на новых томах, включая одноразовую подготовку
прав пустого тома Scout. `integration/compose.existing.yml` подключает к уже работающим
старым сервисам через их Docker-сеть, не запускает их копии и не монтирует их данные.
Установщик сохраняет контрольные IDs старых контейнеров и изменяет только новую CRM
и конфигурацию общего Caddy.
